# 场景清单：这套工具对什么问题负责

每个场景写清：**谁问**、**入口**、**看到什么**、**覆盖状态**。状态以本仓库测试与线上宿主为准；
标「边界」的是有意不做或数据不足做不了的事，不是待办。

## A. 单个技能

| #   | 场景 / 问题              | 入口                          | 看到什么                                                               | 状态     |
| --- | ------------------------ | ----------------------------- | ---------------------------------------------------------------------- | -------- |
| A1  | 「这个技能怎么样？」     | `/skill-eval <skill>`         | 4 维分数、等级、CI、样本数、建议全文                                   | ✅       |
| A2  | 「为什么分低？」         | 同上                          | 维度分解 + 每条建议的证据（比率、样本）                                | ✅       |
| A3  | 「这个技能用得对吗？」   | `/skill-eval <skill>`         | `dead-load`（加载后零调用）、`trigger-collision`（同窗口撞车）         | ✅       |
| A4  | 「它越来越差了吗？」     | `/skill-eval history <skill>` | 逐次加载表 + 前后半段问题率趋势（improving/degrading/flat）            | ✅ 1.9.0 |
| A5  | 「我上次改动有用吗？」   | `/skill-eval impact <skill>`  | 每条被审查编辑前后的错误率对比与判定（improved/degraded/inconclusive） | ✅ 1.9.0 |
| A6  | 「描述写得好吗？」       | 报告 `staticQuality.checks`   | 12 项静态检查（含反触发、kebab 命名、引用完整性）                      | ✅       |
| A7  | 「它引用的文件存在吗？」 | 同上 → `broken-references`    | 缺失路径清单（critical）                                               | ✅ 1.4.0 |
| A8  | 「该删掉它吗？」         | 报告 `prune-candidate`        | ≥6 次加载且分数 <60、区间也低 → 删/合并建议                            | ✅ 1.3.0 |

## B. 跨技能 / 全局

| #   | 场景                           | 入口                                                    | 看到什么                                          | 状态      |

| B1  | 「哪个技能最好/最差？」        | `/skill-eval`                                           | 按分数排序 + 排名显著性（区间重叠时明确说是平局） | ✅        |
| B2  | 「先修哪个？」                 | `/skill-eval loop all`                                  | 按「预期收益/√成本」排序，带 priority 与依据      | ✅ 1.7.0  |
| B3  | 「证据够不够下结论？」         | `/skill-eval validity`                                  | 覆盖数、区间数、以及明确的 Cannot say yet 清单    | ✅ 1.8.0  |

## C. 改动治理

| #   | 场景                     | 入口                                | 看到什么                                                                    | 状态     |
| --- | ------------------------ | ----------------------------------- | --------------------------------------------------------------------------- | -------- |
| C1  | 「改之前先查泄漏」       | `skill_eval_review`                 | reject/warn/accept + 原因码（写死答案、benchmark 名、task id、路径、日期…） | ✅ 1.3.0 |
| C2  | 「改动可追溯吗？」       | 报告 `edits`                        | 假设、维度、裁决、diff hash、时间                                           | ✅ 1.3.0 |
| C3  | 「改完怎么算改好？」     | `/skill-eval impact <skill>`        | 前后错误率 + 判定规则（≥2 次/侧且 >15pp 才算）                              | ✅ 1.9.0 |
| C4  | 「改动有没有引入成本？」 | 报告 `token-cost` / `tokensPerLoad` | 真实 token 归因到窗口，超预算扣效率并出建议                                 | ✅ 1.2.0 |

## F. 配置 / 部署

## G. 明确不支持（边界）

| #   | 场景                          | 原因                                            |
| --- | ----------------------------- | ----------------------------------------------- |
| G1  | 执行技能里的脚本验证正确性    | 评测器不应运行被评对象的代码                    |
| G2  | 读原始 frontmatter 逐字段校验 | DSH 只交付解析后的 summary（只做 id 形态检查）  |
| G3  | 判断"回答内容对不对"          | 没有任务级 verifier；有效性靠下一条用户消息推断 |
| G4  | 自动修改技能并提交            | 只给计划与审查，应用与回滚由人/agent 决定       |
| G5  | 跨机器汇总多份数据            | 单机单 profile 设计；多份数据需自行合并         |
| G6  | 精确到 token 的账单对账       | usage 归因到窗口，不是财务口径                  |
